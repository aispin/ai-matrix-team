## 1. 问题（一句话，必须可回答）

用户要求「**不用我们的模板、出全新设计的设计稿**」时，现行规则是否支持？若支持，按什么模式与授权流程执行？

## 2. 为什么需要你

- **我做不了**：「是否允许脱离既有设计系统出新视觉」属**品牌 / 视觉口径**，按 charter 为 Type 1，须创始人终裁；我无权自我授权改视觉口径。
- **不该替你决定**：换品牌色 / 新视觉方向牵动「矩阵品牌一致性」这个隐含对外承诺，且要动的是**全矩阵共用的出稿规则**。

## 3. 现状取证（为什么这是真问题，不是假设）

| 现行条款（原文） | 位置 | 与「全新设计」的冲突 |
|---|---|---|
| 「**配色一律沿用** examples 默认配色（蓝品牌 #3B5BFD / #6B85FF + 中性灰阶令牌），只搬参考站结构、不搬参考站配色」 | `design-draft.md` 阶段三 L55 | **换品牌色 = 直接违规**（"一律"无例外口） |
| 「模板骨架 = examples…手写路径**从对应场景起步，不从零画框**」 | 同上 | 全新形态**没有「对应场景」**可起步 |
| 「默认出稿路径 = 草稿 JSON + 渲染（省 8 倍）」 | SKILL 阶段三 | 路径惯性：模型倾向套壳，即使需求本该换风格 |

**并且存在内部矛盾**：`design-system.md` 把「品牌色」当作**可指定变量**（L28 四问含「品牌色？」，L171/L176 规定深色品牌色不可自动推导、红橙黄棕系须显式指定），而 `design-draft.md` L55 说「配色一律沿用默认蓝」。**一处允许变、一处禁止动**——设计师即使走正规流程换品牌色，也会先被出稿规则拦下。

**缺的第三样**：没有任何「脱离设计系统」的授权机制（谁能发起、按什么模式、哪些铁律仍适用）。

## 4. 选项

| 方案 | 代价 | 收益 | 推荐 |
|---|---|---|---|
| **甲. 维持现状** | 全新视觉只能靠临时特批，无流程可循；设计师要么违规要么卡住 | 品牌一致性最强 | |
| **乙. 模式 A/B/C 三档判定**（见 §5） | 需维护三档规则与授权链；QA 比样基线按模式区分 | 既有需求不放松，新视觉有正规通道；**矛盾点一并修掉** | ✅ |
| **丙. 完全放开** | 出稿规则只留工程质量铁律，风格全自由 | 最灵活 | 品牌一致性失控（矩阵内页面会散） |

## 5. 方案乙细则（供你审）

### 5.1 三档模式

| 模式 | 触发情形 | 出稿路径 | 授权 |
|---|---|---|---|
| **A · 延续设计系统**（默认，绝大多数需求） | 常规迭代 | 渲染优先（草稿 JSON），不足处 `raw` / 手写 | 无需授权 |
| **B · 视觉换新** | 用户明确要求换品牌色 / 字体 / 气质（形态仍是应用页或落地页） | **走手写**；渲染器**不适用**（组件词汇是既有风格的，套壳反而更差）；可从相近场景起步改造 | 主理人核准 + **报创始人**（Type 1 知会） |
| **C · 全新设计方向** | 新品类 / 新形态（游戏化、杂志风、全新交互范式等） | **走手写**；`examples/` **不再是起点**，允许以用户提供的参考物 / 情绪板起步 | **创始人终裁**；若采纳需另立设计系统条目 |

### 5.2 铁律适用边界（本提案核心）

| 铁律 | 模式 B/C | 判定理由 |
|---|---|---|
| 双主题（浅 + 深，一次给全） | ✅ 适用 | 工程质量 |
| 375px 无横向滚动 | ✅ 适用 | 工程质量 |
| 八态齐全（默认/加载/空/错误/无权限/离线/部分失败/超长） | ✅ 适用 | 验收基线，与风格无关 |
| 图标一律自绘 SVG、禁 emoji | ✅ 适用 | 专业度 |
| 令牌化（不硬编码颜色，走 `var(--*)`） | ✅ 适用（**令牌值可换**） | 可维护性 |
| 每个 UI 区域挂 `data-ui` 标注 | ✅ 适用 | 交接给开发 |
| 配色只用既有默认蓝 | ⚠️ **放宽**：授权后可用新品牌色（深色仍按 `design-system §2.6` 规则 9 单独指定） | 风格 |
| 骨架从 `examples/` 对应场景起步 | ⚠️ **放宽**：B 可从相近场景改造；C 允许不从 examples 起 | 风格 |
| 组件词汇（渲染器 10 类） | ❌ **不适用**：B/C 禁用渲染路径，防套壳 | 风格 |
| 侧栏两段式收起等既定交互 | ➖ **按需**：B 沿用应用形态则保留；C 可重定义 | 风格 |

### 5.3 授权流程（草案）

1. **发起**：设计师在阶段一（需求摘要）注明「视觉换新（B）」或「全新方向（C）」及范围。
2. **判定**：主理人按 §5.1 归档；拿不准按更严一档（C > B > A）。
3. **授权**：B → 主理人核准 + 报创始人；C → 创始人终裁。均落 DR。
4. **执行**：B/C 出稿路径切换为手写；稿头标注「模式 B/C · 未纳入既有设计系统」。
5. **后续**：若新视觉被采纳为正式方向 → 另立设计系统条目（新 examples 场景 + 令牌集），再按频次规则决定是否进渲染器词汇。

### 5.4 矛盾修复（无论选哪档都建议做）

- `design-draft.md`：「配色**一律**沿用默认配色」→「配色**默认**沿用；使用新品牌色须按 §出稿模式 B 走 DR 授权」。
- 「手写路径从对应场景起步」→ 明确标注为**模式 A** 的要求；B/C 见 §出稿模式。
- `design-system.md`：增「模式 B/C 下的适用边界」一节（即 §5.2 表），与出稿规则同源。

## 7. 不做的后果 / 超时行为

- **BLOCKING：不因超时自动执行**（品牌 / 视觉口径不可默认）。超期未答复我会再通报一次；仍无答复则维持现状（方案甲），台账标注「新视觉需求暂无正规通道」。
- 维持现状的已知后果：用户提「全新设计」时设计师只能临时特批或违规，体验上等同「不支持」——这正是本 DR 的提出原因。
