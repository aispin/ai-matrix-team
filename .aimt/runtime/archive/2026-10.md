## ISSUE I-035 guard issues add 的草稿块无正文占位，且 normalize/audit 不检测同号重块（归档 2026-10-21）
来源: ai-matrix-growth PC（2026-10-14：I-023/I-024 曾各出现两块，人工发现） 10-14 · 状态: TRIAGED · 去向: →WO-20261021-01 · 更新: 2026-10-21

**现象**：`guard issues add` 生成的是**只有抬头 + 来源行**的草稿块；调用方（agent）补正文时若在别处「追加一块同号」而不是编辑草稿块本身，文件里就会出现两块同号 I 编号——两块都合法、都 OPEN，`issues normalize` 报「白板已规范」，`audit` 也不告警，只能靠人眼发现。

**复现（本仓项目侧实证）**：ai-matrix-growth 的 `.aimt/issues.md` 里 `I-023`/`I-024` 各出现两块（第一块是 `issues add` 落的草稿、第二块是补正文时追加的同号块），由创始人浏览文档时发现。

**建议**：
1. `issues add` 的草稿块带正文占位（如 `**事实**：（待补）`），让「补正文」有明确落点；
2. `issues normalize`（或 `audit`）增加**同号重块检出**并给出退出码/告警——`## I-<编号>` 在同文件出现 >1 次即告警；
3. 可选：`issues add` 生成草稿后打印「下一步：编辑该块补正文，勿另追加同号块」。

## ISSUE I-036 台账文件 .aimt/{issues,workorders,decisions}.md 未被计入 T 台账面，WO 内登记 issue 后 check --staged 判为越权（归档 2026-10-21）
来源: designer#毛毛 · 状态: TRIAGED · 去向: →WO-20261021-01 · 更新: 2026-10-21

**现象**（0.7.2 · 消费端 ai-matrix-growth）：

1. WO 执行中按纪律发现口径问题 → `guard issues add` 落 `.aimt/issues.md`；
2. 收口 `guard check --wo <id> --staged` 时，`.aimt/issues.md` 被判 **C2 越权**（退出码 2），报错原文：

```
⛔ 越权：以下路径不在 WO 白名单内（扩大白名单须回团长（风控）核准）：
   C2  .aimt/issues.md
```

**根因**：`scripts/surfaces-default.json` 的 T 面规则只有 `.aimt/runtime/**`（与 `.ai-matrix-team/runtime/**`），台账三件套 `.aimt/issues.md`、`.aimt/workorders.md`、`.aimt/decisions.md` 不在其中，落 `defaultTier: C2`。而这三份文件是 guard 自己的写入口（`issues add` / `wo table *` / `dr add`），任何角色单写者模式下都会写。

**后果**：① 每个「WO 中登记 issue」的 agent 都会在收口门禁吃到一次越权告警，或被迫把 `.aimt/*.md` 塞进 WO 白名单（把台账当受控面，与「台账任何角色可写」的语义相反）；② 若 agent 认真对待退出码 2，就会不敢提交台账或不敢登记 issue，纪律被反向激励。

**建议**：把 `.aimt/issues.md`、`.aimt/workorders.md`、`.aimt/decisions.md` 一并纳入 T 面（与 `.aimt/runtime/**` 同级，格式仍由 guard 命令保证），使 guard 自己的写入口与门禁口径自洽。

## ISSUE I-034 LEDGER.md 生成器已移除但消费方仍在读：项目侧台账双源、状态永久陈旧（dashboard 兜底 + inspect 前置）（归档 2026-10-21）
来源: ai-matrix-growth 关单时实测 10-13 · 状态: TRIAGED · 去向: →WO-20261021-02 · 更新: 2026-10-21

**现象**：`.aimt/runtime/decisions/LEDGER.md` 由 `<team-repo>/scripts/ledger-sync.mjs` 维护（文件头自述），但**该脚本已不存在**——
迁移器 `aimatrix-migrate-v2.mjs:19` 还明确写着「LEDGER.md / OPEN-ITEMS.md / closed/ 一律不动（历史只读）」。
于是存量项目的 LEDGER **永久停在生成那一刻**，而消费方还在读它：

| 消费方 | 用法 | 后果 |
|---|---|---|
| `dashboard/server/server.mjs:230-233` | 「旧 LEDGER 兜底（迁移前项目 / 历史视图）」，逐行解析后去重合并 | 已归档的 DR 仍以 `OPEN` 出现在看板 DR 视图（兜底行与 `decisions.md` 的真实状态并存） |
| `scripts/aimatrix-inspect.mjs:198-199` | W8 巡检第 11 项「OPEN-ITEMS 与 DR 台账一致」：只判**存在性**（不存在 → WARN），随后校验各 App `OPEN-ITEMS.md` 条目是否带 DR id | 文件内容陈旧不影响该项判定，但它把 LEDGER 当成"DR 台账"在用，语义已过期 |

**实证**（ai-matrix-growth，2026-10-13）：该仓 LEDGER 仍把两张**已归档**单标为 OPEN——
`DR-20261006-018`（10-06 答复、已执行、10-13 回填归档）、`DR-20261010-001`（10-13 转 `DEFERRED` 归档）。
而现行真相源 `.aimt/decisions.md` 与 `guard report`（D3 修复后实时扫 `decisions.md`）状态都是对的 → **双源不一致**。

**影响**：看板/巡检读到的 DR 状态可能与真实台账矛盾；新人按 LEDGER 判断哪些 DR 还开着会误判；
项目侧也**没有能力**自愈（生成器没了、迁移器又声明该文件只读）。

**建议**（择一，推荐 1）：

1. **退役 LEDGER**：dashboard 去掉旧 LEDGER 兜底、`inspect` 第 11 项改为读 `decisions.md`；LEDGER 是否保留由迁移器统一处理（留指针存根或删）；
2. 保留兜底但**按 `更新` 字段取较新者**（兜底行只在决策源缺失该 id 时生效），并补一条「LEDGER 已废弃」的说明；
3. 恢复 `ledger-sync.mjs` 并纳入 0.7.x 发版脚本（成本最高，且与「台账单一真相源」方向相反）。

**验收**：任一项目 `guard report` 与 dashboard DR 视图的同一 DR 状态一致；`inspect` 第 11 项不再依赖 LEDGER 存在性。

## ISSUE I-039 expert-sync 按 legacyOwnerUid 单一账号登记：多账号机器上只有旧账号能看到专家团，且 --check 永远绿（归档 2026-10-21）
来源: ai-matrix-growth · 状态: TRIAGED · 去向: →WO-20261021-04 · 更新: 2026-10-21

**现象**（0.7.2 · `ed867c5` · WorkBuddy macOS，同一台机器两个 WorkBuddy 账号）：

1. `node scripts/expert-sync.mjs` 跑完，`expert-sync --check` 报 `CHECK OK：全部实例与真源一致`，`guard agents` 全绿；
2. 切到**旧账号**（`e40c2f29-…-personal`）专家中心：「我的专家团」能看到 `ai-matrix-team`；
3. 切到**新账号**（`27977055-…-personal`，2026-10-11 启用）专家中心：「我的专家 / 我的专家团」里**看不到** `ai-matrix-team`，两个独立专家 `aimatrix-team-team-lead`、`aimatrix-team-product-designer` 同样不可见；
4. 包层三处全部正确：`marketplaces/my-experts/.codebuddy-plugin/marketplace.json` 有条目、源包 `plugin.json`（`expertType: team` + `teamInfo.leadAgent` + 5 agents）齐全、`plugins/cache/my-experts/ai-matrix-team/0.7.2` 快照齐全、`plugins/installed_plugins.json` 三条 `@my-experts` 均已登记。

**根因**：专家中心对「本地自定义专家」按**账号白名单**过滤——App 侧 `ExpertPluginService.scanCustomExperts` 扫完 `my-experts/plugins/*` 后，用 `readUserExpertIds(userId)` 读
`~/.workbuddy/experts/custom/<userId>/experts.json`（id 数组）做交集，不在白名单里的包直接跳过。

而 `expert-sync.mjs` → expert-manager `register_expert.py` 只写 marketplace.json + 会话标记，**账号归属由外部状态决定**：
本机 `~/.workbuddy/settings.json` 的 `claw.legacyOwnerUid = e40c2f29-…`，登记结果只落到旧账号目录——

| 路径 | 旧账号 | 新账号 |
|---|---|---|
| `experts/custom/<uid>/experts.json` | 有（含 `ai-matrix-team`） | **整个目录不存在** |
| `storage/user-<uid>-personal/global/expert.json` | 有（recents 内含 `ai-matrix-team`，`expertType: team`） | **不存在** |

即：脚本假定「一台机器一个账号」，多账号机器上第二个账号永远拿不到登记，且脚本没有任何告警。

**影响**：多账号用户（个人号 + 工作号并行，常见）在新账号里专家团"装了但看不见"，排查要一路读 App bundle 才能定位；`expert-sync --check` 只比对 marketplace/cache 两处，
对这种「账号侧漏登记」永远输出 OK，把问题掩盖成"UI bug"。

**建议**（择一或组合，推荐 1+3）：

1. **账号解析改为多账号遍历**：默认对 `~/.workbuddy/experts/custom/*/` 下每个已存在账号都登记（新增 `--all-users`；`--user <uid>` 可指定单个），无账号目录时退回当前行为；
2. **登记后回读校验**：写完读回目标账号 `experts.json`，不含该 id 则以非 0 退出并打印缺了哪个账号——避免静默漏登记；
3. **`--check` 增加账号维度**：除 marketplace/cache 一致性外，检查「每个已知账号的 `experts.json` 是否含团队包与两个独立包 id」，缺失即漂移（退出码 1），并提示补登记命令；
4. 附带（次级）：源包 `marketplaces/my-experts/plugins/<name>/settings.json` 被 WorkBuddy watcher 清掉时，`--check` 只报「运行时以 cache 为准」放行；建议顺手从 cache 自动补齐源包 settings.json，避免每次都要人工还原。

**复现**（最小）：同一台机器存在两个 WorkBuddy 账号目录 → 只在旧账号下放过 expert 登记 → 跑 `expert-sync.mjs` → `--check` 全绿，但新账号专家中心无该团队。

**验收**：同一台机器两个账号，跑一次 `expert-sync.mjs` 后两个账号的专家中心都能看到 `ai-matrix-team`；人为删掉某账号的 `experts.json` 后 `expert-sync --check` 退出码 1 并指名该账号。
