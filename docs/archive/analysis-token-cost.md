## 1. 官方机制（文档结论）

官方《专家中心》文档明确：

- **专家 = 「角色切换」机制**：以「人设 + 方法论 + 工具链」注入会话——三者都要占上下文。
- **专家团 = 「协作执行」机制**：团长自动拆解、**并行派发给多个团员 Agent**、整合交付。
- 专家包结构 = `SKILL.md`（主说明）+ `references/`（参考库）+ `scripts/`（脚本）——官方推荐的分层加载形态。

即：**专家团的 token 成本是「1 个团长会话 + N 个独立团员会话」之和**，每个团员都是一套完整的独立上下文（系统提示 + 角色注入 + 工具 schema），不是便宜的分身。

## 2. 实测量化（本项目）

| 注入物 | 体积 | 注入时机 |
|---|---|---|
| 10 个角色 SKILL.md（aimatrix-*） | **39.2 KB** | 角色被调用时加载 |
| 治理文档 01–08（charter/roles/surface/workflows/rollout…） | **107.5 KB**（02-roles 独占 27 KB） | 角色执行流程时整读 |
| designer references | 40 KB | designer 被调用时 |
| 团员 Agent 注册描述（Agent 工具 schema 内） | 每个团员数百字节 × 8 角色 | 每轮系统提示常驻 |
| `current-expert` 系统提醒（专家工作流注入） | 每轮重复注入 | **每条用户消息** |
| 项目/用户两级 MEMORY.md | 5.2 KB + 用户级更大 | 每会话注入 |
| 每日工作日志 | **137 KB**（单日！） | 被角色「按需」读取时，实际常被整读 |

**乘数因子（这才是「成倍」的主因）：**

1. **每次 spawn 团员 = 一份独立全额上下文**。实测本会话 spawn 4 个子代理**全部被环境击杀、一个都没干活**——但每个的系统提示 + 角色注入 + 工具 schema 照烧。spawn 即成本，与是否产出无关。
2. **spawn prompt 必须 self-contained**：为了子代理自洽，团长要把背景、配方、验收标准整段写进 prompt（本会话 qa prompt ≈ 2 KB/次），回执再算一次。
3. **专家工作流注入每轮重复**：`current-expert` 提醒随每条用户消息反复进入上下文。
4. **文档整读习惯**：治理文档 107 KB 没有分层入口，角色「按需读」实际是整读；27 KB 的 02-roles 每次全量进上下文。
5. **长会话摘要重放**：会话超长触发压缩摘要（summary 本身数 KB）并随会话延续反复出现。
6. **多会话并行 = 线性放大**：每个并行会话都带全套注入（专家工作流 + 记忆 + 角色文档）。

**粗算模型**：一个典型专家团工作会话 ≈ 固定注入（工作流 + 记忆 + 工具 schema）+ 角色文档（50–90 KB ≈ 1.5–3 万 token）+ spawn 成本（每团员数千至上万 token）× 团员数 + 全部工具结果。相比无专家的普通会话，**固定开销 3–5 倍起步，spawn 密集时 10 倍以上**。

## 3. 优化方案（按性价比排序）

### A. 文档分层——把「整读」变「按需读」（收益最大，零功能损失）

- 每个 SKILL.md 瘦身到 **≤150 行**：只留「触发条件 + 流程骨架 + 硬规则清单」，细节全部下沉 `references/`（官方推荐形态，我们只做了形没做实）。
- 治理文档 01–08 拆「索引卡 + 正文」：给每篇生成 ≤30 行摘要卡（谁、何时、读哪节），角色先读卡、按节 `Read`（用 offset/limit），禁止无差别整读。
- 02-roles（27 KB）拆成每角色一页。
- 预期：角色文档注入量降 **60–70%**。

### B. 少 spawn、spawn 小——把「并行执行」变成「按需执行」

- 流程分级：轻判定（风控复核、lint 类 QA）**不 spawn**，由主会话代行 + 备案（本会话已被迫实践，应转正为规则）；只有重活（真机走查、全矩阵回归）才 spawn。
- spawn 预算：团长 prompt 里写死「单次任务 ≤2 个并发团员」；prompt 模板化——**引用文件路径让团员自己读，不粘贴内容**（prompt 从 2 KB 级降到几百字节）。
- 团员 SKILL.md 同样享受 A 的瘦身。

### C. 会话卫生

- **一会话一 WO**：单据粒度 = 会话粒度，干完即收口开新会话（长会话的摘要重放与上下文膨胀比任何单项优化都贵）。
- 每日日志 137 KB → 按单据拆文件（`.workbuddy/memory/2026-10-06/WO-03.md`），日志只留索引；MEMORY.md 严守限额、只放铁律。
- 多会话并行时，非活跃会话及时归档结束，避免「空转带全套注入」。

### D. 工具结果瘦身

- Read 一律带 offset/limit，禁止整读大文件（构建日志 tail、diff 用 --stat 优先）。
- guard/report 增加 `--quiet` 输出模式：人看的详尽、Agent 消费的精简（一行结论 + 证据指针）。
- WO/DR 单据本身（P2 简化后）也是工具结果的一部分——v2 PRD 的「摘要卡」直接减少每次读单的 token。

### E. 度量先行（防盲优化）

- 给 guard 加 `stats` 子命令：统计某单生命周期内「注入物体积 / spawn 次数 / 团员存活时长」，输出一张 per-WO token 成本表。
- 先跑一周拿数据，再决定 B 的分级阈值怎么划。

## 4. 建议的落地顺序

| 步骤 | 内容 | 成本 | 预期收益 |
|---|---|---|---|
| 1 | C 的会话卫生规则 + 日志拆分（写入章程/角色 SKILL） | 半小时 | 立竿见影 |
| 2 | A 的 SKILL.md/references 分层（10 角色 + 01–08 索引卡） | 1 个 WO | 注入量 −60% |
| 3 | B 的 spawn 分级与预算规则（进 charter T 系列） | 规则修订 | spawn 成本 −50%+ |
| 4 | D 的 --quiet 与 E 的 stats | 1 个 WO | 持续可观测 |

## 5. 与 v2 PRD 的关系

- 「单据简化（摘要卡）」同时是 token 优化项（D）——两个迭代可以共享 M1 里程碑。
- 建议把本方案步骤 1–2 并入 v2 PRD 作为 M0（先行批），先降本再上新功能。
