## 1. 机制澄清：WO 上下文是怎么进 LLM 请求的

WO 不进 system prompt，而是经两条通道进入会话，之后**随会话历史在每一轮请求中反复重发**（直至压缩）：

1. **Read 工具结果**：团长写单/派单、implementer 开工读单、QA 读验收标准、风控读意见——每个角色各自整读一遍；
2. **spawn prompt**：为 self-contained 而粘贴的背景/验收标准（Express 模式后 spawn 变少，但团长主会话自身就要读全单）。

关键乘数：**一个 WO 生命周期有 3–4 个独立会话各自付费读同一份单**（团长 / implementer / QA / 收口续会），且单据在会话历史里**存续到会话结束**——30KB 的单 ≈ 1 万 token，在 50 轮的会话里理论重发量是它的 50 倍（有无 prompt cache 视平台实现）。

## 2. 实测量化（2026-10-07）

### 2.1 单据体积

| 族 | 总量 | 单件分布 |
|---|---|---|
| WO open（14 份） | **207 KB** | 中位 ~7 KB，尾部三单 66/33/11 KB |
| WO closed（19 份） | **287 KB** | 最大 51 KB，20–30 KB 常态 |
| DR（open+closed） | **126 KB** | 最大 14.6 KB |
| handoffs（9 份） | **93 KB** | 平均 10 KB，模板仅 1.7 KB |
| reviews/ 技术回执（29 份） | **472 KB（目录 3.6 MB）** | 单份 10–40 KB，被 QA/风控/团长反复引用 |

### 2.2 解剖 65 KB 大单（WO-20261006-03）：过程叙事占 76%

| 节 | 字节 | 占比 | 对后续 LLM 请求的价值 |
|---|---|---|---|
| §9 执行记录 | 36,988 | **56%** | ≈0（事后叙事，只有收口/巡检看） |
| §10 收口 | 13,421 | **20%** | ≈0（同上） |
| §8 风控意见 | 7,333 | 11% | 低（结论行足矣） |
| §2 白名单 + §5 验证 + 头部 | ~5,700 | 9% | **高**（guard 机器解析 + 派单授权必需） |
| 其余（背景/类型/影响/回滚/DR） | ~11,600 | 18% | 中（开工读一次） |

**结论：创始人直觉成立。** 单据越滚越大，76% 是追加式过程叙事；而模板把 §9/§10 放在同一个文件里，导致每次「读单」都把 4 倍于必要信息的字节拉进上下文，还要在每个角色会话里重复付一遍。

### 2.3 伴生放大器（同样未在上轮优化覆盖）

- **reviews/ 技术回执 472 KB**：单据引用它们，角色「按需读」实际整读（老问题在新族重演）；
- **当日日志已 35 KB**（22 个时段块）：v1.5 只拆了 10-06 历史日志，当日日志的膨胀速度（一天 35 KB）意味着跨天会话读「今日上下文」的成本在回升；
- **共享台账 shared-contracts.md 34 KB**：每次契约登记前后都要核对，整读一次 ≈ 1.2 万 token；
- workorders/INDEX.md 14.6 KB、instances.json 3 KB——轻，但常驻扫描面。

## 3. 优化方案（按性价比排序）

### A. WO 单据三层化（本主角，收益最大）

把「机器面 / 调度面 / 叙事面」拆开：

1. **主文件（≤6 KB 硬上限）**：头部表格 + **TL;DR ≤10 行**（做什么/怎么算完成/当前状态）+ §2 白名单 + §5 验证命令 + §7 DR 表 + 变更类型。guard parseWo 所需全在这层。
2. **journal 文件（同目录 `WO-xxx.journal.md`，append-only）**：§8 风控意见全文、§9 执行记录、§10 收口明细全部改追加到这里。追加用 `guard wo journal <单号> "条目"` 类命令**机器写入**——LLM 只发增量条目，不发旧文；主文件里只留一行指针（「过程叙事见 journal」）。
3. **归档时**不合并（closed 单保持「主文件 + journal」对），巡检按需读 journal。

预期：**每次读单从 8–65 KB 降到 ≤6 KB**（−70～90%），一个 4 会话生命周期的单据读付从 ~40 KB×4 降到 ~6 KB×4。

### B. 读单纪律（规则极轻，立即可做）

- implementer/QA 只读 §2/§5/TL;DR（行号锚点写在 TL;DR 里）；整读全文仅限收口与巡检；
- 派单 prompt 一律**引用路径+节号**，禁止粘贴单据内容（第一轮 B 的未完成半步）。

### C. 回执与意见瘦身

- 成员回执 ≤15 行：文件清单（含面域）+ 验证输出尾行 + 遗留/DR 链接，其余进 journal；
- 风控/QA 意见落 journal 用「结论行 + 证据指针」，不粘贴对话或代码。

### D. 配套族治理

- reviews 技术回执 ≤200 行硬上限（超了拆 appendix 文件，正文留指针）；
- shared-contracts.md 按域分节 + 登记时只读相关域（节锚点已在维护，补进 SKILL）；
- 当日日志按「单据块」写，单据收口时把该块移入 topic 文件（当日日志只留活跃块）；跨天会话禁止整读昨日全量。

### E. 度量与平台杠杆

- guard `stats` 增加 per-WO 视角：单据字节数 / journal 字节数 / 被引用 reviews 字节数——落地 A 后看下降曲线；
- 向平台确认两件事（第一轮开放问题未决）：① prompt cache 是否生效（决定「历史重发」的真实成本）② `current-expert` 每轮注入可否降频。

## 4. 建议落地顺序

| 步骤 | 内容 | 成本 | 预期 |
|---|---|---|---|
| 1 | B 读单纪律 + C 回执瘦身（改 SKILL/charter 各一节） | 半个 WO | 立减 30–40% |
| 2 | A 单据三层化（模板改造 + `guard wo journal` 命令 + 存量单迁移规则「新单新办法」） | 1 个 WO | 读单成本 −70%+ |
| 3 | D 配套族上限 + 日志增量归档 | 并入步骤 2 | 防 SQL（review/日志）反弹 |
| 4 | E stats 扩展 + 平台确认 | 并入步骤 2 | 可观测 |
