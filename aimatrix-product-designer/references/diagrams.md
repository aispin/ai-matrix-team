# 图示规范（什么时候用哪种图 · 怎么画）

> **效力与本位**：本文件是「用图说话」这一表达形式的**真相源**，与 [`design-system.md`](design-system.md) 并列、互补——`design-system.md` 管**界面**（组件 / 图标 / 双主题 / 状态），本文件管**论证与说明用图**（定位图 / 管线图 / 流程图 / 对照表）。
> **不重复的部分**：图标本身（24×24 网格、stroke 统一、坐标偶数、`currentColor`）一律按 `design-system.md` §3 执行，本文件不重述，只补「图」这一层的额外约束。
> **适用对象**：BRD/PRD/勘误/评审记录里的示意图、汇报用 SVG 图、设计稿内的结构说明图。
> **一条总原则**：**图的任务是把「比较」和「关系」一眼讲清；不是让文档好看。** 讲不清的，退回文字或表格。

---

## 0. 三步选型（先选型，再动手）

```
第 1 问：这里要表达的是「比较」还是「关系」？
  ├─ 比较 → 维度 ≤ 3 且 方案 ≤ 2   → 两轴定位图（§2）
  ├─ 比较 → 方案 ≥ 3 或 维度 > 3   → 多方案对照表（§5，用表，不用图）
  └─ 关系 → 上游/下游、多对一      → 单一真相源管线图（§3）
     关系 → 用户旅程 / 学习闭环   → 闭环流程图（§4）
     关系 → 单点结论 / 纯数值     → 不画图（§8）

第 2 问：这张图讲几件事？
  只讲一件事 → 继续；超过一件 → 拆成两张图（节点上限 5，见 §6）

第 3 问：图里的每个数字 / 术语，能在正文里指到出处吗？
  能 → 继续；不能 → 先在正文补出处，或标「待确认」（§6 第 9 条）
```

## 1. 四种范式总览

| 范式 | 用在什么问题上 | 形态 | 节点上限 |
|---|---|---|---|
| **两轴定位图**（§2） | 2–4 个候选方案要选一个，取舍有对立的两面 | 一张散点 + 一条取舍分界 | 4 |
| **单一真相源管线图**（§3） | 一套数据多处呈现 / 多条来源汇入一个结构 | 三段式横向管线 | 5 |
| **闭环流程图**（§4） | 用户旅程 / 学习闭环 / 商业闭环 | 纵向线性 3–5 步 + 回流注记 | 5 |
| **多方案对照表**（§5） | 3 个以上方案 / 维度超过 3 个 | 表（**不是图**） | — |

**一句话记法**：**能比较的用轴，有汇流的用管线，有来回的用流程，选项多的一律用表。**

---

## 2. 范式一 · 两轴定位图

### 2.1 什么时候用

- 有 **2–4 个候选方案**（能力档位、内容策略、渲染路线、付费墙位置……），需要在两个**互相拉扯**的评价维度上比出取舍。
- 结论是「**推荐落在哪一格**」以及「**分界线画在哪**」，而不是「哪个更好」。

### 2.2 怎么画（照这个顺序做）

1. **选两条对立的轴。** 必须是「此消彼长」的关系（如 交互深度 ↔ 传播拉新力、实现成本 ↔ 用户价值、内容自由度 ↔ 合规可控性）。如果两条轴能同时变好，那不是一对轴，是同一个维度，换掉。
2. **写清两端含义。** 每个轴的四个端点（高 / 低）都要有字面标注，**不允许只画箭头不写字**。轴的名称 + 高端含义 + 低端含义，三样缺一不可。
3. **候选点 ≤ 4 个**，用**不同色但同一色阶**（同一主色的四个明度阶，或主色 + 三档中性）。禁止一图四色四个色相。
4. **画取舍分界**。若结论是「分界之后才值得做」（如付费墙、能力门槛），在轴上画一条**虚线**并标注分界含义；不画分界的定位图等于没有结论。
5. **正上方一句话结论**（如「推荐落在右上格：交互深度换传播力，代价是成本上浮」）。
6. **正下方一行口径说明**，写清数据来源与口径（哪个文档、哪个版本）。
7. 给每个候选点**配文字标签**（点号 1/2/3/4 用形状 + 数字，不用 ✓ ★ 之类的符号），评审时才能精确引用「方案 3」。

### 2.3 禁用

- 用两条能同时变好的轴（假对立）。
- 只靠点的颜色区分方案（色盲 / 黑白打印即失效，必须配编号 + 文字）。
- 把 5 个以上方案塞进一张定位图 —— 改走 §5 对照表。

## 3. 范式二 · 单一真相源管线图

### 3.1 什么时候用

- 「**一套数据多处呈现**」：同一结构被两个以上消费端读取（卡片渲染 / 剧场渲染 / 导出、Web 端 / 桌面端）。
- 「**多条来源汇入一个结构**」：内置内容 + AI 生成 + 社区投稿，最后归一化成同一份结构。
- 结论是「**为什么不会分叉**」，以及「**新增一个来源 / 新增一个消费端时改哪里**」。

### 3.2 怎么画

1. **固定三段式**：`来源（1–2 个）` → `统一结构（1 个）` → `消费端（1–2 个）`。三段用三列，**列宽一致**，中间列可以更高。
2. **中间那层必须显式标注「单一真相源」**（一个胶囊标签，或层标题），这是整张图的论点所在，不能靠读者猜。
3. **箭头方向单一，不画回头箭头。** 来源 → 结构 → 消费端，一条道走到黑。如果确实存在反向写入，**另起一张图**讲「写回路径」，不要在同一张图里制造双向箭头。
4. **消费端一律标「它读什么」**（读 `scene.turns` / 读 `scene.stage`），而不是标「它长什么样」。
5. **缺省 / 降级路径写在正下方口径说明里**，不要画成图上的分支线（图里多一条分支 = 结论被稀释）。
6. 中间结构与来源、消费端的**命名必须逐字沿用正文术语**（正文写 `Scene` 就不要写成「场景对象」）。

### 3.3 禁用

- 把中间层画成「转换器 / 适配层」链（一层变两层，读者就不知道哪个是真相源）。
- 在图上标注实现细节（函数名、文件名可以，但不要标行号、库版本、性能数字）。
- 汇流箭头画成多条曲线扭在一起 —— 用**正交直线**（横向主线 + 45° 折角），不用曲线。

## 4. 范式三 · 闭环流程图

### 4.1 什么时候用

- 用户旅程（进入 → 互动 → 反馈 → 结算 → 产出）。
- 学习闭环 / 商业闭环（供给 → 使用 → 产出 → 回流成新供给）。

### 4.2 怎么画

1. **3–5 步，不要更多。** 第 6 步说明其中两步其实是同一件事，合并。
2. **每步一行主标题 + 一行说明**（纵向排列，横向卡片，一行一步）。主标题是动作词（4–6 字），说明写**规格 / 机制**，不写形容词：
   - 写「锚 `stage.turnIndex`」，不写「沉浸式体验」；
   - 写「积点入账」，不写「超有成就感」。
3. **循环不要画成圆环。** 用**线性流程 + 收尾处的「产出回流」注记**：最后一步下面接一条**虚线**连到一个虚线注记块，注记里写「产物回流带来新 X，重新进入第 1 步」。圆环一旦画出来，中间必然空，读者要绕圈找起点；线性读，一眼到底。
4. **步骤编号用「形状 + 数字」**（圆形 / 圆角方块底 + `1 2 3`），**不用 ① ② ③ 这类文字符号**（`design-system.md` §3.1：符号当图标一律禁止）。
5. **正上方一句话结论**（这条闭环卖的是什么 / 回到哪里），**正下方一行口径说明**（计费、口径、术语出处）。
6. 结尾若有未定案环节（尚未定稿的机制），把它标成「（待确认）」并保持中性色，**不要因为要闭环就把它写成已定案**。

### 4.3 禁用

- 圆环 / 环形箭头 / 莫比乌斯带（好看但读不出起点）。
- 每步塞两句以上说明 —— 超了就把说明挪到图下的口径行。
- 用「世界给反馈」这类文学化标题去替代机制说明；主标题可以是业务语言，说明必须是机制。

## 5. 范式四 · 多方案对照表（图之外的「表」）

### 5.1 什么时候用「表」而不是「图」

**三条任一命中，就用表：**

1. 方案 ≥ 3 个；
2. 比较维度 > 3 个；
3. 需要**精确读数**（成本、影响面、点数、行数、占比）。

### 5.2 表格规格

- **行 = 方案，列 = 维度 + 推荐列**；最后一列固定为「推荐 / 落点」。
- **表里只放可比较的事实**（成本 / 影响面 / 不可逆性 / 影响文件数 / 是否触发 DR），**不放形容词**（「体验好」「更优雅」一律不合格）。
- 不确定的量级写「**待测算**」或「**待确认**」，并用备注列说明谁给数据、什么时候给；**不许猜一个数字填进去**。
- 推荐列用「**推荐 / 备选 / 不做**」三值，**不要用勾叉符号**；推荐项可在方案名后加一个字面后缀「（推荐）」。
- 表格宽度控制在正文可读范围，**长文本进备注列**，不要靠列宽硬塞。

### 5.3 禁用

- **把表格画成图**（三方案六维度画成六边形雷达图 → 读者读不出数值，只看到形状）。
- 表里出现「更简单」「更好用」这类不可比较项。
- 缺推荐列（评审完不知道选哪个）。

## 6. 风格硬约束（每一条都是硬性要求）

1. **扁平单色阶**：每张图 **≤ 2 个色系** = 主色（1 个）+ 中性灰阶。主色只用来强调**论点所在的那一层 / 那一点**，其余交给中性灰。
2. **禁渐变、禁阴影、禁发光、禁装饰性插画。** 层级靠**明度与描边**，不靠滤镜。
3. **禁 emoji，禁文字符号充当图标**（`◎ ▲ ★ ✓ ✕ ➜ ①`、`⚙ → ★` 全部禁止）——与 `design-system.md` §3.1 一致，出现即重做。段落文字里表「顺序」用「·」或逗号，表「流向」用**画出来的箭头**。
   - **判定口径（主理人 2026-10-12 裁定，与 AC-9 同源）**：禁令只作用于**图标位与正文标签位**；`<desc>`/`<title>` 无障碍描述、源码注释等**散文位置的箭头字符（如 U+2192 →）不计违规**——那里它承载语义而非装饰，改成 `->` 反而更差。落图自查时用"是否充当图标"判定，不要用字符黑名单一刀切。
4. **节点 ≤ 5**；每张图**只讲一件事**；超过就拆图。
5. **版式固定三层**：**正上方一句话结论**（图名即结论）→ 图 → **正下方一行口径说明**（数据来源 / 版本 / 计费口径 / 术语出处）。图中的每个数字都必须能在这行里指到出处。
6. **术语一律沿用正文**，不引入新词、不造缩写。中英混排时**中文为主**（代码标识符、专有名保留原文）。
7. **深浅主题都要可读**：颜色走**主题令牌**，或写成对的浅色底 / 深色底取值（浅色一套、深色一套，显式写出）。**不硬编码单套色值**——交付前必须切深色看一遍，白底穿帮即重做。
8. **SVG 交付形态**（可直接被 Markdown / HTML 引用或内联）：
   ```svg
   <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 680 H" width="100%"
        role="img" aria-labelledby="t d">
     <title id="t">图名（= 一句话结论）</title>
     <desc id="d">口径说明全文（供屏幕阅读器与检索）</desc>
     <style>
       /* 令牌作用域 = 本图 svg 元素：不污染宿主文档的 :root 令牌 */
       svg{color-scheme:light dark;font-family:'PingFang SC','Nunito',-apple-system,sans-serif;
           --ink:#2f3446;--ink-soft:#6b7280;--line:#ece7f3;--card:#fff;--accent:#6c7be0;--accent-tint:#eef0fb}
       /* 深色一 · 跟随系统：img 引用与直开 .svg 都生效 */
       @media (prefers-color-scheme:dark){
         svg{--ink:#e8eaef;--ink-soft:#9aa2b1;--line:#2d3542;--card:#1a1f28;--accent:#8e9bef;--accent-tint:#20263a}
       }
       /* 深色二 · 内联到宿主文档时，跟随宿主「跟随系统 + 手动切换 + 记忆偏好」的显式结果 */
       html[data-theme="dark"] svg{--ink:#e8eaef;--ink-soft:#9aa2b1;--line:#2d3542;--card:#1a1f28;--accent:#8e9bef;--accent-tint:#20263a}
       html[data-theme="light"] svg{--ink:#2f3446;--ink-soft:#6b7280;--line:#ece7f3;--card:#fff;--accent:#6c7be0;--accent-tint:#eef0fb}
     </style>
     <!-- 图：矩形 + 圆角矩形 + 正交直线 + 文字，零外部依赖 -->
   </svg>
   ```
   - **宽 680 固定**（`viewBox="0 0 680 H"`，`H` 按内容定），`width="100%"` 自适应容器；
   - **零外部依赖**：不引字体文件、不引 JS、不引图片（字体走系统栈 `'PingFang SC','Nunito',-apple-system,sans-serif`）；
   - **不写死 `#hex`**：所有填充与描边走上面的 CSS 变量；
   - 深色底**不用纯黑**（按 `design-system.md` §2.6 规则 1，画布 `#0f1319`），深色下**不靠阴影**分层。
9. **数字与口径的唯一真相源是文档**：图里只能出现正文已定案的数字；引入新数字前先在正文定案。未定案项标「**（待确认）**」并保持中性色，**不得让未定案项看起来已定案**。
10. **同类图在同一文档内必须同风格**：同一份 BRD/PRD 里的所有图共用一套令牌、同一字号阶梯、同一描边宽度。

## 7. 反模式（出现即重做）

1. **一张图塞多条分支** —— 主线被分支稀释，读者记住的是分支不是结论。修法：主图只留主线，分支拆第二张图，或下降为表。
2. **把表格画成图** —— 三维以上、可精确读数的比较（成本 / 影响面 / 点数）画成雷达图、气泡图，等于把可比较的事实变成不可读的形状。修法：改 §5 对照表。
3. **用颜色单独承载信息** —— 只靠颜色区分方案 / 状态，黑白打印或色盲用户即失效。修法：颜色之外再加**编号 + 文字标签**（`design-system.md` §5.4「状态标签用『点 + 文字』」同理）。
4. **轴没有单位或含义** —— 只画两条带箭头的线、端点不写字，图就退化成装饰。修法：轴名 + 高端含义 + 低端含义，三样齐。
5. **图与结论不一致** —— 结论写「推荐右上」，图里右上却是空点。修法：出图后**从图反读一遍结论**，反读不出来就重画。
6. **同一文档内换风格** —— 上一张图圆角 12、下一张圆角 4，上一张主色强调层、下一张主色强调点。修法：同文档共用一套令牌，新图从既有图复制骨架改文字。
7. **在一张图里塞下所有节点** —— 节点超过 5 个，读者开始数数而不是理解。修法：合并同类项，或拆图。
8. **图上出现未定案数值却不标注** —— 把「待测算」写成具体数字，评审会当成已定案。修法：标「（待确认）」+ 口径行写明谁提供。
9. **文字符号 / emoji 当图标**（`🚀 ✂ ▶ ★ ✓ ➜ ①`）。修法：自绘 SVG，或改用「形状 + 数字」。
10. **图里出现形容词**（「沉浸式」「优雅」「强大」）。修法：改成机制 / 规格 / 可观测事实。

## 8. 何时不要画图

| 情形 | 用什么 | 为什么 |
|---|---|---|
| **单点结论**（「改 / 不改」） | 一句话 + 理由 | 一个点没有关系可画，画出来只有装饰 |
| **纯数值对比**（成本、点数、覆盖率、行数） | 表格 | 读者要的是读数，不是形状 |
| **需要精确读数** | 表格，或真正的统计图表（折线 / 柱状，带坐标轴与刻度） | 示意图没有刻度，读不出数；要么补刻度做成真图表，要么退回表 |
| **线性步骤极少**（2 步） | 一句话 | 两个节点画流程是浪费版面 |
| **关系只在一句话里说得清** | 文字 | 图是把文字**压缩**，不是把文字**摊开** |
| **数据未定 / 出处不明** | 先补出处，暂不出图 | 图会替未定案的数字背书 |

**判断口径**：如果这张图删掉后，读者仍能从文字得到同样结论，那这张图不该存在 —— 要么删掉，要么改成表。

## 9. 交付与落盘

- **单张图 = 单个 `.svg` 文件**（不是截图、不是 PNG），放该 App 的设计资产目录（`apps/<app>/docs/design/`），命名用 `语义-语义.svg`（小写连字符，如 `pipeline-single-source.svg`、`loop-learn-and-share.svg`）。
- **该目录必须有 `README.md` 作资产索引**：列全部资产 + 引用本文件作规范真源（**引用不复述**）。
- 图在正文里以**链接**出现，**不在正文里内联粘贴 SVG 源码**（改一次要改两处）；需要内联时（如设计稿 HTML）直接读 `.svg` 文件内联，仍只维护一份真源。
- 结论行、口径行的文字与 `.svg` 内的 `<title>` / `<desc>` **保持同文**，检索与无障碍同时成立。
- 出图后**必做**：① 切深色看一遍；② 缩到 375px 宽看一遍（是否仍可读、无横向滚动）；③ 从图反读结论一遍。

## 10. 图示自检清单（交付前逐条打勾）

**选型**
- [ ] 这张图确实是图（关系 / 比较），不是表能解决的事（§8）
- [ ] 范式选对：能比较用轴、有汇流用管线、有来回用流程、选项多一律用表

**结构**
- [ ] 节点 ≤ 5，只讲一件事
